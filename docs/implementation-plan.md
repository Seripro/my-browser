# 学習用ミニブラウザ 実装方針

## ゴール

SwiftUIとWebKitの`WKWebView`を使い、URL入力、戻る、進む、再読み込み、読み込み状態の表示ができるmacOSアプリを完成させる。

## 全体像

```text
BrowserApp（SwiftUIアプリの入口）
  └─ BrowserView（URLバーと操作ボタン）
       └─ WebView（SwiftUIからWKWebViewを利用するための橋渡し）
            └─ WKWebView（Webページの表示・履歴・読み込み）
```

SwiftUIはボタンやURL入力欄を表示する。`WKWebView`はWebページの取得と表示を担当する。両者をつなぐ`WebView`を`NSViewRepresentable`として実装する。

## ステップ 1: 開発環境を確認する

### 実施内容

1. Xcodeをインストールする。
2. Xcodeを起動し、macOS Appテンプレートで新しいプロジェクトを作成する。
3. Interfaceは`SwiftUI`、Languageは`Swift`を選択する。
4. アプリが起動し、初期画面が表示されることを確認する。

### この段階で分かること

- macOSアプリはXcodeプロジェクトとしてビルド・実行される。
- `App`がアプリの入口であり、`WindowGroup`がウィンドウを作る。

### 完了条件

Xcodeからアプリを実行できる。

## ステップ 2: 静的なブラウザ画面を作る

### 実施内容

1. 既存の`ContentView`を`BrowserView`として扱う。
2. 上部にツールバー風の領域を置く。
3. 戻る、進む、再読み込みのボタンを置く。
4. URL入力用の`TextField`を置く。
5. 下部に「ここにWebページを表示する」というプレースホルダーを置く。

### この段階で分かること

- SwiftUIは状態を基に画面を記述する。
- `HStack`、`VStack`、`TextField`、`Button`で基本的なUIを構成できる。

### 完了条件

ブラウザらしい見た目の画面が表示される。各ボタンはまだ動作しなくてよい。

## ステップ 3: WKWebViewを表示する

### 実施内容

1. `WebView.swift`を作成する。
2. `NSViewRepresentable`に準拠した`WebView`を定義する。
3. `makeNSView`で`WKWebView`を生成する。
4. プレースホルダーを`WebView`へ置き換える。
5. 起動時に例として`https://example.com`を読み込む。

### この段階で分かること

- SwiftUIの画面内でAppKitの`NSView`を使うために`NSViewRepresentable`を使う。
- `WKWebView.load(URLRequest)`がページ読み込みを開始する。
- WebKitが通信、HTML/CSS/JavaScriptの処理、描画を担う。

### 完了条件

アプリ内に`example.com`が表示される。

## ステップ 4: URL入力からページを開けるようにする

### 実施内容

1. URL入力欄の文字列を`@State`で管理する。
2. Enterキーを契機にURLを検証して`WKWebView`へ読み込みを依頼する。
3. `http://`または`https://`がない入力には`https://`を補う。
4. URLとして解釈できない文字列では読み込まず、入力欄の近くにエラーを表示する。

### URL処理のルール

- `example.com` → `https://example.com`
- `https://example.com` → そのまま開く
- `http://example.com` → そのまま開く
- 空文字列またはURLとして不正な値 → 開かずにエラーを表示する

### 完了条件

入力した有効なURLのページが表示される。

## ステップ 5: ナビゲーション操作をつなぐ

### 実施内容

1. `WKWebView`の参照を、SwiftUI側から安全に操作できる形で保持する。
2. 戻るボタンで`goBack()`を呼び出す。
3. 進むボタンで`goForward()`を呼び出す。
4. 再読み込みボタンで`reload()`を呼び出す。
5. `canGoBack`と`canGoForward`に応じて各ボタンを有効・無効にする。

### この段階で分かること

- WebViewはブラウザ履歴を内部に保持する。
- UIの状態と`WKWebView`の状態を同期する必要がある。

### 完了条件

リンク遷移後、戻る・進む・再読み込みが期待通り動作する。

## ステップ 6: 読み込み状態と現在URLを同期する

### 実施内容

1. `WKNavigationDelegate`を使い、読み込み開始・完了・失敗を検知する。
2. 読み込み中は`ProgressView`などを表示する。
3. ページ遷移が完了したら、URL入力欄を現在のURLへ更新する。
4. 読み込みエラー時は、失敗したことをUIに表示する。

### この段階で分かること

- `WKNavigationDelegate`は、WebViewのナビゲーションイベントをアプリへ通知する。
- ページ内リンクによる遷移も、URLバーへ反映する必要がある。

### 完了条件

ページ読み込み中であることが分かり、完了後にはURL欄が表示中ページのURLになる。

## ステップ 7: 最低限の使い勝手を整える

### 実施内容

1. 起動時にURL入力欄へフォーカスを当てる、または初期ページを開く。
2. ツールバーがウィンドウ幅に応じて自然に伸縮することを確認する。
3. 戻る・進むができないときの無効状態を確認する。
4. URL入力欄でEnterキーを押してもボタンが二重に実行されないことを確認する。
5. 少なくとも複数のHTTPSサイトで表示・リンク遷移を試す。

### 完了条件

通常のWeb閲覧を短時間試せる品質になっている。

## ステップ 8: 振り返りを記録する

実装後、`docs/requirements.md`の完了条件に照らして動作を確認する。次の内容もメモする。

- アプリ側が担当したこと
- WebKit側が担当したこと
- 次に追加したい機能
- 今回あえて対象外にした機能

## 実装順序の原則

- 1ステップごとに起動・動作確認してから次へ進む。
- 最初から状態管理を複雑にしない。必要になった時点で`ObservableObject`などを導入する。
- 外部ライブラリは導入しない。
- うまくいかないときは、SwiftUIのUI、`WKWebView`の表示、両者の状態同期のどこで問題が起きたかを分けて確認する。

## 初版で触れない注意事項

ダウンロード、複数ウィンドウ、新規タブ、ポップアップ、認証ダイアログ、権限要求、独自のセキュリティポリシーは初版の対象外とする。これらはWebブラウザとして重要だが、最小版の学習範囲を超えるためである。
